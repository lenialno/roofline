# Квантование: выбор и проверка

## Что выбирать

1. Есть официальная FP8-версия модели (или Hopper/Blackwell и checkpoint в bf16): FP8. Память вдвое, decode быстрее, качество почти без потерь, tool calling сохраняется
2. Нужно уместить модель, которая в FP8 не влезает: AWQ или GPTQ 4-bit (в vLLM через `compressed-tensors`, AWQ, GPTQ-Marlin). Проверять tool calling обязательно
3. KV cache в fp8 отдельно от весов: удваивает число запросов в KV при той же памяти; потеря качества мала, но проверяется на длинном контексте
4. QAT-модели (например gpt-oss в MXFP4) уже откалиброваны, их не переквантовывать
5. Самостоятельная PTQ-калибровка (NVIDIA ModelOpt, llm-compressor): калибровочный набор из своих промптов (код, инструменты), не из общих датасетов

## Протокол приёмки

| Шаг | Критерий |
|---|---|
| Перплексия на 50-100 своих документов, одна токенизация | рост не больше 1-2% против bf16 |
| `task smoke-toolcall` | PASS, включая stream и roundtrip |
| Набор задач агента (20-50 реальных задач: прочитать, исправить, запустить) | доля успешных не ниже bf16 минус 2 п.п. |
| `task bench` при рабочей конкурентности | TPOT p95 ниже, чем у bf16; TTFT не хуже |
| Длинный контекст (fp8 KV) | ответ на вопрос по 50k-документу совпадает с bf16 |

Признаки деградации от квантования: JSON с лишними запятыми или кавычками в аргументах, повторяющиеся токены, вызов инструмента с перепутанными параметрами, пустой ответ после `</think>`.

## Почему tool calling страдает первым

Аргументы инструмента должны быть точным JSON: одна ошибка в токене ломает вызов целиком, тогда как в прозе та же ошибка незаметна. 4-битные веса сдвигают распределение на редких токенах (скобки, кавычки, имена параметров). Перплексия может вырасти незначительно, а доля валидных вызовов упасть заметно, поэтому smoke и задачи агента обязательны, а перплексии недостаточно.
