# Рабочий лист sizing

Пример: команда 20 разработчиков на Claude Code через прокси, модель Qwen3-32B FP8, 2 x H100 80 GB с NVLink.

| Шаг | Расчёт | Результат |
|---|---|---|
| Веса | 32.8B x 1 Б (FP8) | 33 ГБ |
| KV на токен | 2 x 64 x 8 x 128 x 1 Б (fp8 KV) | 128 КБ |
| Память доступна | 2 x 80 x 0.90 минус 33 минус 2 x 3 (накладные) | 105 ГБ |
| Токены в KV | 105 ГБ / 128 КБ | около 860k |
| В полёте на запрос | промпт p95 40k плюс ответ 1k | 41k |
| Concurrency при p95 | 860k / 41k | 21 запрос |
| Concurrency при p50 (промпт 20k) | 860k / 21k | 41 запрос |
| Нагрузка | 20 пользователей x 10 вызовов/мин / 60 = 3.3 RPS; e2e средняя 6 с | 20 одновременных |
| Вывод | одна реплика TP=2 держит с запасом при p50, на пределе при p95 | `max-num-seqs 32`, следить за `waiting` |

Проверка: `task vram MODEL=/models/Qwen3-32B-FP8 GPU_GB=80 TP=2 CTX=65536 KV_DTYPE=fp8 AVG_TOKENS=24000`, затем `task bench BENCH_C=16 BENCH_IN=20000 BENCH_OUT=512`.

## Когда расчёт врёт

- Prefix cache: токены общего префикса хранятся один раз; реальная concurrency выше расчётной, если префикс стабилен
- Reasoning-модели: ответ с размышлением в 3-10 раз длиннее; считать по p95 выходных токенов
- MoE: веса целиком в памяти, выигрыш только в скорости decode на запрос
- Chunked prefill: длинные промпты не блокируют decode, но общий compute тот же; TTFT при холодном промпте 50k на одной реплике это секунды
- Накладные: cudagraph, активации, буферы NCCL; при TP больше 1 закладывать 3-4 ГБ на GPU
- Контекст выше нативного (Qwen3-32B: 40960) требует YaRN в профиле, иначе сервер не стартует или качество на длинных промптах падает; флаг смотреть через `task flags Q=rope`
